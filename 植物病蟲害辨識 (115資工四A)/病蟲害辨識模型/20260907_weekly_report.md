## 1. 摘要

- **本期用預先登記的判準同時關掉了兩個方向。** 一是模型容量（v12s），二是部署端的匯出參數調校；兩者都不是憑印象判斷，而是達標線在開跑前就寫死。
- **v12s 判準未通過：模型參數放大 3.84 倍，test mAP50 只從 0.80959 變成 0.81266，增加 0.00307**，僅為 0.03 門檻的十分之一，且遠低於本專題量過的 run 間全距 0.021。**結論是模型容量不是瓶頸。**
- **九個類別中只有一類的變化超過 ±0.04 的 per-class 雜訊地板**，四類變好、四類變差、一類不動。若容量真的是瓶頸不會呈現這種分佈，尤其第二弱的 `Citrus_Leaf_Miner` 反而掉了 0.024。
- **這是模型端連續第四輪無效**，累計十一種改動。唯一有效過的手段仍然是資料端的標註重整。因此 **m 尺度不需要再試**：s 尺度的 3.84 倍參數只換到雜訊等級的差異，m 尺度沒有理由不同，成本卻會再上去。
- **部署端已量清楚：測試裝置達不到 30 FPS**，精度可用的最佳組合為 15.42 FPS。完整數據見〈[YOLO26-nano-P2 匯出參數與行動端延遲全面掃描報告](../%E7%B3%BB%E7%B5%B1%E6%B8%AC%E8%A9%A6%E8%88%87%E8%A9%95%E4%BC%B0/yolo26n_p2_export_params_benchmark.md)〉。

## 2. 背景與方法

本期要回答的是一個明確的問題：**模型容量是不是本專題精度的瓶頸？** 在此之前，模型端的架構與損失函數改動已連續三輪未通過顯著性門檻，但「換一個更大的模型」始終沒有被實際測過。

### 2.1 單一變因設計

v12s 相對 v11.5 **只改一個變因：模型尺度由 nano 換成 small**。預訓練權重、排程、全部超參數、資料集版本與切分方式逐字相同。

| 項目 | v11.5 | v12s |
| --- | ---: | ---: |
| 參數量 | 2,518,088 | 9,667,624（3.84 倍） |
| GFLOPs（640） | 7.65 | 26.67（3.49 倍） |
| epochs 與 patience | 70 與 0 | 70 與 0 |
| 其餘超參數 | — | 完全相同 |

訓練中 `batch=20` 沒有發生記憶體不足，未曾降低批次大小，**所以本輪確實是純粹的尺度比較，沒有混入其他變因**。

### 2.2 判準為何訂在 0.03，以及為何事先訂

達標線 test mAP50 大於等於 0.83959（v11.5 的 0.80959 加 0.03）是**開跑前就寫死在訓練腳本第一格**的，不是事後決定。理由有兩項實測依據：

- **per-class 雜訊地板約 ±0.04**：在 v11 上，資料完全沒有改動的類別也會移動這個幅度。
- **run 間全距 0.021**：v10、v11、v11.5 三個版本在完全同一批影像上的 test mAP50 為 0.809、0.800、0.788。

低於 0.03 的差距無法與這兩種雜訊區分，所以事先約定那不算數。**先訂判準再跑實驗，結果才有拒絕的能力。**

### 2.3 訓練協定

一律採 `patience=0`、固定輪數、報告 `last.pt`。這是 v11.5 起確立的協定：`best.pt` 由 valid 挑出，一旦採用 `best.pt`，valid 就參與了決策而不能併入評估集；改報 `last.pt` 之後 valid 可合法併計，評估誤差從只報 test 的 ±0.140 降到 ±0.099。

## 3. v12s：模型容量是不是瓶頸

### 3.1 判準裁決

#### 表 3-1：整體指標對照

| 指標 | v11.5 | v12s | 差異 | 判讀 |
| --- | ---: | ---: | ---: | --- |
| test mAP50 | 0.80959 | 0.81266 | **+0.0031** | 雜訊內 |
| test mAP50-95 | 0.60691 | 0.61836 | +0.0115 | 雜訊內 |
| valid mAP50 | 0.82899 | 0.83652 | +0.0075 | 雜訊內 |
| valid mAP50-95 | 0.63580 | 0.64345 | +0.0077 | 雜訊內 |

表 3-1 顯示四個指標全部落在雜訊範圍內，主要結果 test mAP50 的增幅只有達標門檻的十分之一，**判準未通過**。

表 3-2 是本輪最有說服力的證據：四類變好、四類變差、一類不動，只有 `Scale_Insect` 勉強越過 ±0.04 的雜訊地板。**若容量真的是瓶頸，應該看到多數類別同向改善，尤其是最弱的那幾類；但第二弱的 `Citrus_Leaf_Miner` 反而變差 0.024。** 這個分佈就是「沒有系統性改善」的樣子。

### 3.3 成本

#### 表 3-3：放大模型的代價

| 項目 | v11.5 | v12s | 倍率 |
| --- | ---: | ---: | ---: |
| 訓練時間 | 3.06 小時 | 4.91 小時 | 1.61 倍 |
| 每輪耗時 | 157 秒 | 253 秒 | 1.61 倍 |
| 最佳輪次 | 第 53 輪 | 第 69 輪 | — |
| 行動端推論延遲（依實測外推） | 266 ms | 約 950 ms | 3.5 倍 |

表 3-3 顯示訓練成本的增幅（1.61 倍）遠低於 GFLOPs 的增幅（3.49 倍），代表 nano 尺度時 GPU 並未吃滿，資料管線是相當大的固定成本；但**推論端沒有這個緩衝**，因此 v12s 在行動端約 1.05 FPS。

> **v12s 不是候選部署模型。** 行動端連 nano 尺度的 266 ms 都離 30 FPS 差 6.8 倍，small 尺度只會更遠。它的定位是精度上限探索，用來回答容量是不是瓶頸，答案是不是。

### 3.4 附帶確認的三件事

- **`patience=0` 與 `last.pt` 的協定再次成立**：`best.pt` 與 `last.pt` 在 test 與 valid 上的差距全部小於等於 0.0007，且方向不一致。`best.pt` 高出平台期僅 0.77 個標準差，是歷來最小（v10 為 2.8、v11 為 2.7、v11.5 為 1.5）。
- **評估精度維持達標**：九個類別的 pooled ±2SE 最差為 0.099（`Citrus_Leaf_Miner`），全數小於等於 0.10。
- **本輪對兩項事前預測的修正**：原先預測參數放大後會提早過擬合、最佳輪次應早於第 53 輪，實際是第 69 輪且完全沒有過擬合跡象；訓練時間原估 7.6 至 9.1 小時，實際 4.91 小時，誤在以 GFLOPs 線性外推訓練時間。**往後估訓練時間不可用 GFLOPs 外推**，推論端可以，訓練端會高估。

## 4. 模型端的累積結論

### 表 4-1：模型端四輪改動的結果

| 輪次 | 改動內容 | 結果 |
| --- | --- | --- |
| v9 六臂消融 | Wise-Inner-MPDIoU（兩種比例）、ADown、StarTripletBlock、輸入解析度 800 | **零臂通過 2 個標準差門檻** |
| v10 至 v11 至 v11.5 | 三次訓練協定與資料切分調整 | 同一批影像上全距 0.021，等於 run 間變異 |
| **v12s** | **模型尺度放大 3.84 倍參數** | **+0.003，等於雜訊** |

表 4-1 顯示模型端已連續四輪、累計十一種改動全部無效。**唯一真正有效過的手段是資料端的標註重整**：v5 至 v5r 的標註尺度統一讓 Thrips 的 AP50 從 0.572 提升到 0.749，用的是原封不動的官方架構。

由此得出兩條明確的停損：**不要再試 m 尺度模型**（s 尺度的 3.84 倍參數只換到雜訊等級的差異，m 尺度的 21.07 M 參數沒有理由不同，訓練與推論成本卻會再上去）；**不要再從模型端找改善**。

## 5. 全案盤點與後續方向

### 5.1 三條線的現況

| 線 | 現況 | 成熟度 |
| --- | --- | --- |
| **資料集** | v5.6：9 類，train 7,264、valid 401、test 401；九類評估誤差 ±2SE 全部小於等於 0.10；全類別零跨 split 近重複；增強造成的標註框膨脹缺陷已修 | 量尺已達標，但兩個類別的**標註品質**仍是開放問題 |
| **模型** | 交付基準為 v11.5（test mAP50 0.80959）；訓練協定已固定 | **已走到底**，四輪十一種改動全部無效 |
| **部署** | 本期新開；22 組量完整 mAP、18 組量實機延遲；最佳可用組合 15.42 FPS | **已量清楚**，官方參數已窮盡 |

本期最大的結構性變化是第三條線從無到有。在此之前專案只有精度這一把尺、量不出延遲，「要不要換更大的模型」根本無法討論，因為不知道有多少預算可用。

### 5.2 還開著的問題

| 問題 | 卡在哪 | 需要什麼 |
| --- | --- | --- |
| **`Thrips_Damage` AP50 僅 0.489** | 成因是**標註框定義不一致**，valid 與 test 差 0.202，三輪都沒有隨評估集擴大而收斂。補樣本量救不了 | 人工標註一致性測試：兩人各標 20 張，中位 IoU 大於等於 0.85 才值得全類重標，否則依既定規則刪除該類別 |
| **`Citrus_Leaf_Miner` AP50 僅 0.652** | 樣本量少，原始影像僅 111 張 | 外部影像 150 張補標框 |
| **達不到 30 FPS** | 官方匯出參數已窮盡，僅剩量化感知訓練與直接在 320 解析度訓練兩條路，都須重訓 | **需先確認產品端是否真的需要即時串流** |
| 結論只成立於一台裝置 | 目前只有 CPH2641 | 第二台測試裝置 |

**上表前兩項是目前唯一還沒試過的方向。** 容量、架構、訓練協定與匯出參數都已排除之後，剩下的手段都在資料端，而資料端卡在人工，不卡在技術。

### 5.3 下一步的兩個決策點

1. **30 FPS 是不是真的需要。** 若互動形式是對準葉片後拍照出結果，64.8 ms 的單張延遲使用者不會察覺，320 解析度的 fp32 現在就可以交付；若必須是即時串流，本裝置做不到，需換硬體或重訓。這是產品決策，技術面已經量清楚。
2. **人工標註工作是否發派。** 兩包工作的規格與判準都已備妥且尚未開始，這是精度線上唯一還有機會的方向。

## 6. 結論與限制

1. **模型容量不是本專題的精度瓶頸。** 3.84 倍參數換到的 0.00307 與同設定重跑一次的隨機變異無法區分，判準未通過。
2. **模型端已無可投入的方向。** 四輪十一種改動全部無效，預算應移回資料端。
3. **現行交付基準維持 v11.5 的 YOLO26-nano-P2。** v12s 不進入部署候選。
